# 个性化推荐与管理员维护优化设计

## 1. 背景

当前个性化推荐存在两个直接问题：

1. 用户选择“自然风光”并补充“喜欢山水”时，主推荐可能是“历史文化爱好者路线”。
2. 管理员维护页面同时暴露景点、路线节点、步行边、讲解素材、权重和导入配置，操作对象与数据关系不清晰。

本设计同时优化推荐准确性和管理员维护体验。运行时仍然从推荐数据库读取数据，原始 Word、Excel、JSON 只作为导入来源。

## 2. 已确认的根因

推荐算法目前会把路线模板标签与路线内所有可评分景点标签合并。历史文化路线中的部分景点也带有 `nature` 标签，因此历史文化路线会被判定为自然兴趣完全命中。

当自然路线与历史路线的兴趣分相同时，当前排序可能退化为按路线名称排序。用户截图中的 120 分钟场景中，两条路线都得到相同的兴趣、满意度、热门程度和时间匹配结果，最终历史路线因名称排序排在前面。

此外，补充描述字段目前没有进入核心评分；管理员页面中的部分编辑操作调用新增接口，可能把编辑保存为重复记录。

## 3. 目标

### 3.1 推荐目标

- 用户选择自然风光时，主推荐优先来自路线自身标记为自然风光的路线。
- 景点标签只能辅助判断路线内部内容，不得改变路线的主主题。
- “山水、湖景、园林、风景、自然”等补充描述可以归一化为自然风光兴趣。
- 无完全匹配路线时，允许返回相近路线，但必须明确标记为相近推荐。
- 推荐结果能解释匹配原因，便于管理员和用户发现资料问题。

### 3.2 管理目标

- 默认页面围绕路线卡片组织，不要求管理员理解数据库表结构。
- 导入先预览、校验、去重，再正式写入。
- 日常操作只需要导入、审核、预览、快速编辑和启用/停用。
- 高级能力继续保留，但放入高级编辑入口。
- 编辑已有景点、路线和素材时必须更新原记录，不能重复新增。

### 3.3 本轮 MVP 边界

本轮拆成三个紧密相关但边界清晰的交付单元：

1. 推荐算法与结果解释：修复主题误命中、补充描述归一化和确定性排序。
2. 导入与编辑语义：补充 dry-run 预览结果，修复编辑误新增，并完善重复提示。
3. 管理员简单模式：将已有管理能力重新组织为路线卡片和高级编辑入口。

MCP 内容校验、路线健康检查接口、历史数据库批量清理和完整发布工作流不作为本轮实现内容，先保留接口扩展位置。

## 4. 推荐算法设计

### 4.1 两阶段候选筛选

用户兴趣由显式标签和补充描述推断标签组成，显式标签优先保留，推断标签只补充不覆盖。多个兴趣取并集；重复标签去重；未知词忽略；两者都为空时视为无主题偏好。

第一阶段判断路线主题：

- 只使用启用且至少有一个可评分节点的路线模板。
- `direct_match`：路线模板自身兴趣标签与用户兴趣交集不为空。
- `general_match`：用户没有提供任何可识别兴趣时，所有可用路线进入综合排序。
- 路线内景点标签不再把路线从 `similar_match` 提升为 `direct_match`。
- 如果存在 `direct_match`，只从直接匹配路线中生成主路线和备选路线。
- 如果没有直接匹配，再从其他启用路线中选择 `similar_match`；只有 `stop_match > 0` 的路线进入相近候选，不解析路线摘要。
- 如果用户没有兴趣，使用 `general_match`，按时间、强度和质量排序。
- 如果没有任何可用路线模板，才保留现有“动态推荐路线”兜底；如果连启用景点也没有，则返回“暂无可推荐路线”。

第二阶段的确定性排序键依次为：

1. 匹配类型：有兴趣时 `direct_match` 优先于 `similar_match`；无兴趣时使用 `general_match`。
2. 路线主题命中率降序：命中的路线主题数量除以用户兴趣数量，范围为 0 到 1，保证多主题请求优先选择命中主题更多的路线。
3. 总分降序。默认总分为 `0.60 * interest_match + 0.15 * time_fit + 0.15 * intensity_fit + 0.05 * satisfaction + 0.05 * popularity`；管理员在高级配置中调整权重时，先将五项权重归一化到总和 1。
4. 时间适配分降序：`max(0, 1 - abs(route_minutes - budget_minutes) / budget_minutes)`；没有预算时为 0.8。
5. 强度适配分降序：`max(0, 1 - abs(route_difficulty - target_difficulty) / 3)`；没有体力偏好时为 0.8。
6. 数据库路线 ID 升序，作为最终稳定排序键，不再使用名称排序。

`interest_match` 为 `0.7 * theme_match + 0.3 * stop_match`。直接匹配路线的 `theme_match` 为命中路线主题数除以兴趣数；`stop_match` 为可评分景点中命中兴趣的景点数除以可评分景点数。相近路线的 `theme_match` 为 0，只在 `stop_match > 0` 时进入相近候选。无兴趣时 `interest_match` 固定为 0.5。

`route_difficulty` 为可评分景点难度的算术平均值。`satisfaction` 只对大于 0 的景点满意度求平均后除以 5；没有有效值时为 0.5。路线原始热度为大于 0 的景点热度平均值；候选路线最大原始热度大于 0 时，用路线原始热度除以该最大值，否则所有候选的 `popularity` 为 0.5。所有分数先按未舍入浮点值排序，对外的分项保留 3 位小数，总分保留 4 位小数。

本轮只将兴趣、补充描述、游览时长和体力强度纳入用户侧评分。室内外、避开事项和同行人字段暂不宣称会影响排序，后续实现前需单独定义规则。

### 4.2 兴趣归一化

用户兴趣标签继续使用稳定的内部值，例如 `nature`、`history`、`family`。补充描述通过轻量关键词映射归一化：

- 山水、湖景、园林、风景、自然、看景：`nature`
- 古迹、佛教、历史、文化、建筑：`history`
- 亲子、孩子、儿童、互动：`family`
- 拍照、打卡、摄影：`photo`

显式兴趣与补充描述冲突时取并集。例如显式选择历史文化、补充描述写“喜欢山水”，请求同时包含 `history` 和 `nature`，系统返回同时命中两个主题的路线优先。补充描述中没有可识别关键词时不改变显式兴趣。

该映射只在推荐请求中使用，不引入每次请求实时调用 MCP 的不确定性。

### 4.3 结果解释

每条路线增加可解释信息：

- 匹配类型：主题匹配、相近推荐、综合推荐或动态兜底。
- 命中的兴趣主题。
- 时间是否合适。
- 强度是否合适。
- 触发的风险或降级原因。
- 统一的 `match_type` 枚举：`direct_match`、`similar_match`、`general_match`、`dynamic_fallback`。
- `match_label` 根据主题命中率显示“完全主题匹配”或“部分主题匹配”，避免把只命中一个兴趣的多主题请求描述成完全匹配。

用户页面可以显示一句简短原因，管理员页面可以查看更完整的评分拆解。

## 5. 管理员页面设计

### 5.1 简单模式

页面默认进入简单模式，内容包括：

- 顶部状态摘要：已启用路线、导入待处理项、数据风险。
- 主操作：导入并审核、新增路线、刷新。
- 路线卡片：名称、兴趣主题、节点数量、预计时长、启用状态和风险。
- 路线操作：预览推荐、快速编辑、启用或停用、进入高级编辑。

本轮不新增独立发布状态字段。现有 `enabled=true` 显示为“已启用”，`enabled=false` 显示为“已停用”；启用即允许参与推荐，停用即不参与推荐。“导入待处理”只表示最近一次 dry-run 的未处理问题，不持久化为路线状态。风险提示包括重复景点、缺少兴趣标签、草稿点位、未维护步行时间和没有可推荐节点等。

### 5.2 高级编辑

高级编辑继续提供完整能力，但按路线聚合：

1. 路线基础信息：名称、摘要、兴趣主题、时长、强度和启用状态。
2. 路线时间轴：添加景点、调整顺序、设置停留时间。
3. 讲解素材：按景点和兴趣主题维护讲解内容。
4. 步行时间：维护路线中相邻景点的步行信息。
5. 推荐策略：使用全局预设并作用于全部路线。五项顺序为兴趣、时间、强度、满意度、热门程度：“优先兴趣匹配”为 `0.70/0.10/0.10/0.05/0.05`，“均衡推荐”为 `0.50/0.20/0.15/0.10/0.05`，“优先时间合适”为 `0.40/0.35/0.15/0.05/0.05`。自定义值必须是有限非负数且总和大于 0，保存时归一化到总和 1。
6. 导入日志：查看导入来源、处理结果和错误信息。

### 5.3 导入审核

导入流程使用现有试运行能力：

1. 上传或粘贴完整数据包。
2. 校验 JSON 结构、必填字段、数值范围、枚举值、包内唯一性和引用完整性。
3. 先执行 dry-run，不写入数据库。
4. 返回新增、更新、跳过、无变化和错误的互斥动作数量，并单独返回重复问题数量及逐条问题记录。
5. 仅当没有阻断错误或冲突时允许确认；警告可以确认，但必须在结果中展示。
6. 管理员确认后在一个事务中正式导入；任一写入错误时整体回滚。

实体校验规则：景点和路线必须有名称；兴趣标签必须是已知标签或明确标记为自定义标签；停留时间和步行时间不能为负数；节点顺序必须为正整数；路线引用的景点和路线必须存在于当前包或数据库；步行边的起点和终点不能相同。

身份匹配优先级固定为：`external_id` 身份表、导入包显式数据库 ID、自然键。身份表按“实体类型 + external_id”唯一保存，支持跨次导入稳定匹配；自然键比较前统一 trim、合并连续空白并使用 casefold。若身份表目标已软删除、身份键与自然键分别指向不同记录，或自然键匹配到多条活动记录，均生成阻断冲突，不自动选择记录。没有稳定编号时：景点按名称匹配，路线按名称匹配，节点按路线 ID 加顺序匹配，素材按景点 ID 加兴趣标签加标题匹配，步行边按起点 ID 加终点 ID 匹配。匹配到已有记录时生成“更新”，未匹配时生成“新增”；包内同一匹配键出现多次时生成“重复”错误，不自动选择其中一条。

dry-run 返回结构化结果：汇总数量、逐条动作、错误级别、错误代码、字段路径、错误消息和目标记录 ID。`malformed_json`、缺少必填字段、非法数值、未知枚举、悬空引用、稳定编号冲突和包内重复键属于阻断错误；更新已有记录、跳过项和已有相同内容属于可确认警告。每条记录只有一个 `action`：`create`、`update`、`skip`、`unchanged` 或 `error`；问题另有独立的 `level`：`warning` 或 `error`。汇总按 action 互斥计数，问题按 level 和错误代码单独计数；“重复数量”来自重复相关错误代码，不作为 action。

正式确认会在 SQLite 事务中重新执行同样的校验和身份匹配，不保存长期预览令牌。预览后若身份目标被软删除，则返回 409 身份冲突并整体回滚；若没有身份映射的自然键目标被删除，则按当前数据库重新判断为新增；若目标被其他操作修改，则更新当前活动记录，并在实际结果中返回新的动作统计。任一校验或写入错误都整体回滚，前端以正式结果为准刷新列表。

## 6. MCP 知识库边界

本轮不实现 MCP 调用，只保留后续接入边界。未来 MCP 可用于资料加工阶段：校验景点主题标签、补充景点摘要和讲解素材、识别同义名称。MCP 不可用时，导入和推荐必须继续使用本地规则完成；MCP 也不直接决定游客请求的最终路线，不绕过管理员审核写入生产数据。

## 7. 接口与数据边界

优先复用现有推荐管理接口，不立即改变数据库主结构。需要补充或调整的能力包括：

- 推荐结果返回 `match_type`、`match_reasons` 和稳定的 `score_breakdown`。
- 导入接口在 dry-run 模式下返回 `summary` 和 `issues`，正式导入返回相同动作统计。
- 前端编辑已有记录使用 PUT，且 PUT 为完整替换；新记录使用 POST；DELETE 继续执行软删除；启用或停用通过现有 PUT 更新 `enabled`。软删除记录不参与推荐，本轮不提供恢复接口；更新不存在的 ID 返回 404，匹配键冲突返回 409，字段错误返回 400。
- 讲解素材增加已有记录的更新能力，避免编辑变成重复创建。
- 简单模式的路线风险先由前端基于已加载路线、节点和步行边计算，不新增健康检查接口。

推荐结果的关键枚举和字段：`match_type` 为 `direct_match`、`similar_match`、`general_match` 或 `dynamic_fallback`；`match_reasons` 为面向用户的短文本数组；`score_breakdown` 包含 `interest_match`、`time_fit`、`intensity_fit`、`satisfaction` 和 `popularity`。

导入身份表包含 `entity_type`、`external_id`、`entity_id`，并对前两者建立唯一约束。导入预览的 `summary` 计数互斥；`issues` 每项包含 `level`、`code`、`path`、`message`、`action` 和可选的 `target_id`。字段错误返回 400，身份冲突返回 409，事务执行失败返回 500 并保证不保留部分写入。

## 8. 测试策略

后端测试：

- 自然兴趣请求优先返回自然路线。
- 历史路线中的自然景点标签不会把历史路线变成自然主路线。
- “喜欢山水”可以识别为自然风光。
- 无完全匹配时返回相近推荐标识。
- 显式兴趣与补充描述取并集，未知词和重复词不会破坏结果。
- 直接匹配、相近匹配、动态兜底和无结果四种路径均有测试。
- 没有兴趣时进入 `general_match`；没有可用节点时返回明确的无结果信息。
- 时间、强度和缺失数据不会破坏候选排序。
- dry-run 不产生数据库写入。
- 损坏 JSON、缺少必填字段、悬空引用、重复稳定编号和非法数值会返回结构化错误。
- 正式导入发生错误时事务整体回滚。
- 导入身份表可以让相同 `external_id` 的重复导入保持幂等。
- 排序测试覆盖主题命中率、总分、时间、强度和路线 ID 的完整平分链。
- 权重预设值、负数/非数字/全零权重校验均有测试。
- 身份冲突、软删除目标、自然键多匹配、PUT 全量替换和停用记录不参与推荐均有测试。
- 编辑景点、路线、素材不会产生重复记录。

前端测试：

- 简单模式展示路线卡片和风险摘要。
- 高级编辑入口可以打开完整维护能力。
- 导入结果展示新增、更新、重复和异常信息。
- 快速编辑已有记录调用更新接口。
- 推荐结果展示匹配原因或相近推荐提示。

## 9. 非目标

本轮不实现以下内容：

- 不在游客每次请求时实时调用 MCP 重新规划路线。
- 不在本轮实现 MCP 内容加工调用。
- 不引入地图导航或实时道路规划。
- 不删除已有高级维护能力。
- 不新增独立的路线发布状态字段；先使用现有启用字段。
- 不直接清理现有数据库中的重复数据；先通过导入预览和编辑更新逻辑阻止继续产生重复，历史数据清理另行处理。
